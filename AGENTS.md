# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

## 3D Asset Production

- Production-visible laboratory assets must follow [`docs/3d/ASSET_PIPELINE.md`](docs/3d/ASSET_PIPELINE.md). Start from references and an asset specification; preserve real dimensions, recognizable anatomy, intentional hierarchy/pivots, articulated spatially relevant parts, physically credible material roles, optimized GLB delivery, and visual validation in LabSpace.
- Three.js and React Three Fiber are the real-time renderer and interaction layer, not the default final modeling method for detailed equipment. Do not accept a complex asset that still looks like a few untouched runtime boxes, cylinders, or planes merely because that is faster to code.
- Simple primitives remain preferred for collision, placement and snapping proxies, raycast/selection volumes, clearance zones, debugging, hidden construction primitives, and explicitly labeled temporary placeholders. Starting a professional Blender or Blender-Python model from primitives is valid; shipping a crude primitive-looking final visual is not.
- Keep the authored visual mesh separate from lightweight spatial logic. Extend the existing catalog, dimension, storage-rig, and placement systems rather than creating competing metadata or using dense render geometry for collision.
